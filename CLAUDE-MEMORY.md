## kicad-concurrent-edit-hazard

The user works in the KiCad GUI on the same `.kicad_pcb` that my scripts are
writing, in the same session. A GUI save writes KiCad's whole in-memory board,
silently reverting every script change made since KiCad last loaded the file.

This actually happened 2026-08-19 on Open-Secure-ESC: their save reverted a
rule area and 30 silkscreen moves, and my `git add -A` committed the reverted
board under a message asserting DRC numbers I had measured before their save.
The commit's own blob had 56 violations where the message claimed 16.

**Why:** `git status` being clean means the working tree matches HEAD. It does
NOT mean nobody else edited the file — when their save has already been swept
into one of my commits, clean status means exactly the opposite.

**How to apply:**
- Before committing after any long tool sequence, re-run the verification
  against the file *as it is on disk now*, not the numbers measured earlier.
- Check `pgrep -a kicad` and for `.lck` files before writing a board; if KiCad
  is open, say so rather than writing over unsaved GUI work.
- Prefer explicit `git add <path>` over `git add -A` when a tool sequence
  spans many minutes.
- When the user says an edit is on disk and `git status` is clean, look for
  their change *inside recent commits* before concluding it is missing.
- A GUI-moved footprint usually leaves the zone fill stale, which shows up as
  a clearance ERROR that a refill clears. Refill before judging their edit.
